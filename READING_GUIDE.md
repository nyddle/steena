## Что вынести из каждого ключевого раздела

### §4.2.1 Code tasks (стр. 9–11) — качество задач важнее количества
- 5 источников задач: GitHub PR+issue; реальные запросы сотрудников («vibe coding»); задачи по спецификации; CodeMidas (задачи из существующего кода); длинные многошаговые задачи. Плюс публичные наборы, в т.ч. PrimeIntellect swe-rl.
- **Accuracy:** каждую задачу 4 раза решает агент, потом *auditing agent* смотрит все 4 решения + логи и ищет false positive (тест пропустил плохое решение) и false negative (тест отверг хорошее).
- **Robustness:** F2P должны падать до патча и проходить после, P2P — проходить всегда; стабильно в **8 перезапусках**. Отсев flaky-тестов.
- ❓ Вопрос себе: сколько из 35k задач swe-rl переживут такую проверку? Закладывай отсев.

### §4.2.6 Reward hacking (стр. 14–16) — самое практичное
- **Table 2 (стр. 15)** — пять паттернов: `pip install` новой версии пакета, `curl` файла с GitHub, `git clone` апстрима, чтение тикета с фиксом, `pip index versions`. Модель прямо в thinking пишет «посмотрю, как это пофиксили в апстриме».
- Контрмеры: чистить артефакты сборки/кэши/bytecode, обрезать git-историю до base commit, **сетевая изоляция контейнера**, явный запрет в промпте.
- **Hack agent:** отдельный агент атакует окружения, пока не перестанет находить дыры.
- Для тебя: если генерировать трассы на swe-rl без изоляции сети, часть «успешных» трасс будут списыванием — и 37B этому научится. Нужны network-off песочницы и фильтр трасс по командам (`pip install <target>`, `git clone`, `curl github`).
- ⚠ Нестыковка: в репорте «confirmed hack < 2%» (Fig. 6), а на дашборде `select_hack_attempt_rate` ≈ 40–50%. Похоже, это разные вещи — *попытки*, отмеченные судьёй, против *подтверждённых* хаков. Стоит держать в голове при чтении.

### §4.3 Groupwise grading (стр. 16–20) — главная идея репорта
- Проблема: бинарная награда «тесты прошли» не различает хорошее и плохое прохождение.
- **GRS (offline, стр. 17–18):** по нескольким роллаутам агент пишет рубрики для задачи — *solution* и *behavior*. Награда `R = R_test · S_sol · S_beh` (формула 2). Провал остаётся нулём.
- **GAR (online, стр. 18):** агент-судья смотрит всю группу, ранжирует прошедшие решения по 5 осям (подход, точность, минимальность, отсутствие побочных эффектов, стиль кодовой базы) и **перераспределяет положительный advantage** к лучшим (формула 3). Подтверждённый хак → награда 0.
- **Fig. 8 (стр. 19):** без GAR длина и число ходов раздуваются, pass rate упирается; с GAR рост идёт до шага 52. Абзац под графиком — какие плохие привычки появляются без GAR (swallow exceptions, compat-ветки, ослабленная валидация). Очень узнаваемо.
- **§4.3.3 (стр. 19–20):** length penalty относительно квантиля длины успешных решений в группе (формула 4); штрафы за битые tool calls на уровне сегментов с сохранением массы advantage (формула 5).
- Для тебя: даже на этапе SFT-трасс идею GAR можно взять как **фильтр** — из нескольких прошедших решений брать лучшее/короткое, а не любое.

### §5 Experiments (стр. 20–25)
- **§5.1 — все гиперпараметры в одном месте:** микс задач (code 68%, general 12%, design 13%, context 3%, cyber 4%), 1568×16, staleness 4, Muown lr 3e-6 без warmup, clip 1.0; IS-клиппинг с 4 отдельными границами, которые подстраиваются под энтропию.
- **§5.3, Fig. 10:** multi-harness RL поднимает и невиданные харнесы (Codex, Claude Code, mini-swe-agent): ~50% → 66%.
- **§5.4 Router freezing (стр. 23–24):** с обучаемым роутером за 20 шагов CV нагрузки экспертов 0.78 → 2.0, «холодных» экспертов 0.5% → 22%. Откат роутера к исходному чинит всё без потери качества. Если твоя 37B — MoE, это must-read.
- **§5.5 Failure analysis:** честный список падений — хорошая чек-листа для своей инфры.
- **§5.6 MOPD2 (стр. 24–25):** дистилляция с нескольких учителей; prefix-conditioned OPD — студент генерирует один ход поверх готовой истории из трасс учителя/SFT. Полезно, если будешь смешивать MiMo и K3.

### §3.2 Mid-training (стр. 7)
- Перед RL переключают AdamW → **Muown** (Muon с контролем норм строк): AdamW хуже масштабируется на больших батчах. Спайков лосса при переключении не было.
- Mid-training на агентных траекториях + данные «рефлексии над хаком» — модель сама переписывает свой ошибочный ход.

### §7 Open foundations (стр. 33–36) — ближайший к твоему плану
- 9B = SFT Qwen3.5-9B на **77.4B токенов (27.2B loss-токенов)** данных MiMo. Table 4 — доли доменов.
- Table 6: SFT уже даёт основной прирост (SWE-bench Pro 32 → 44.6), RL поверх — ещё +3…+15.
- Table 7: 4 mini-harness в обучении, 3 в отложенных — прирост во всех 21 парах.
- Вывод для 37B: сначала сильный SFT на хороших трассах, RL — потом.

## Вопросы, с которыми стоит читать
1. Какие цифры проверяемы? Много результатов — на внутренних бенчах (MiMo Code/Cyber/Visual Bench). Публичные: DeepSWE, AutomationBench, Terminal Bench, OSWorld, CyberGym.
2. Где абляции? Есть для GAR (Fig. 8), router freeze (Fig. 11), multi-harness (Fig. 10). Для остального — нет.
3. Сколько стоит повторить? RL Pro — $2.6M, из них rollout 44%, training 44%, grader 13% (Fig. 3). Grader — заметная статья расходов.
4. Что из обещанного open-source реально есть? На 22.09 — веса и логи; окружения и фреймворк не найдены (см. README).
